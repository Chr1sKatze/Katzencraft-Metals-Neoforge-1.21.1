# Foundry crafting and safe dismantling

All four recipes are generated by `ModRecipeProvider`. Every D position uses the item
tag `katzencraftmetals:foundry_deepslate`, so variants can be mixed. Its eight full cubes
are Deepslate, Cobbled, Polished, Bricks, Cracked Bricks, Tiles, Cracked Tiles and Chiseled
Deepslate. It excludes ores, infested/reinforced blocks, slabs, stairs and walls.

- Controller: `DDD / DFD / DDD`, F = Furnace.
- Tank: top/bottom rows are space-D-space; middle is `DGD`. G = ordinary Glass, not panes.
- Table: `S S / DDD / DPD`, S = Smooth Stone Slab, P = `minecraft:planks`.
- Basin: `D D / D D / DDD`.

Each crafts one registered block item and has a Deepslate recipe unlock.

## Mining

Tank `getDestroyProgress` returns exactly 1/160 per tick on client and server, bypassing
player/tool speed calculations. Native mining interruption and Creative instant breaking
remain native. Tanks do not require a correct tool for drops; their loot is one tank item.
The Controller uses the existing level-3 requirement and normal pickaxe mining speed.

## Ownership and persistence

Active molten contents remain pooled in `FoundryControllerTankStorage`. Geometry,
rendering, density ordering, per-height capacity and all casting/processing paths use the
existing network facade. Tank blocks still have no block entity or ticking inventory.

Controller removal stops its ticker and discards unfinished jobs. Its molten snapshot is
transferred to dimension-local `katzencraftmetals_foundry_vessels` SavedData before its
storage is cleared. Tanks are not destroyed. A replacement Controller claims complete
overlapping snapshots once, removing their escrow before using the recovered contents.
Partial claims, overlapping records and overwriting active contents are rejected.

Detached storage does not process or resume jobs. Chunk-watch snapshots synchronize
immutable visual copies of its exact contents to clients. A world-render callback uses
the same liquid mesh, smoothing, shaders, glow, hotspots and smoke with those snapshots;
it never claims or changes storage. Full vessel layouts determine layer heights even
when only some chunks are visible. Unwatch/disconnect clears replicas. Controller
reconnection sends active block state/data before retiring the detached visual source;
active Controller draws also suppress overlapping detached views during handoff.
No separate molten inventory, liquid mesh, overlay or shader was introduced.

The Controller BER explicitly uses ordinary render buffers for remote tank liquid and
hatches. Minecraft's Controller destruction-buffer wrapper must not reach those vertices.
The Controller block and individual tanks retain their normal targeted block-model cracks.
Snapshots now preserve their original Controller render origin (animation/smoke phase);
older detached saves without this optional field use their anchor.

## Destruction transaction

The tank's normal removal callback captures storage before resolving dirty Controller
caches. It excludes the removed tank, follows mutual logical connections, and chooses
one component containing the Controller attachment, or the persisted anchor without a
Controller. If that component violates the existing simple-fluid shape validation, a
deterministically grown valid anchored subset survives. Ordinary placement/incomplete
construction is not automatically dismantled.

Before automatic removals, survivor contents are committed once. Reentrant callbacks
are guarded. Every rejected tank is removed through server `destroyBlock(pos, true)`;
there is no second manual item spawn. Native neighbor updates and the final Controller
structure/storage update use the existing synchronization path. The nearby-controller
search is bounded and resolves adjacent chunks instead of interpreting an unloaded
Controller as absent.

## Whole-unit accounting

The old implementation merely trimmed top-layer overflow to fit the new capacity. That
could retain metal from removed lower tanks and discard metal belonging to survivors.

Removal now apportions the **pre-edit** pooled contents by horizontal Y layer and metal
density, matching existing equalized capacity. Storage has integer molten units; equal
fractional shares cannot be stored independently. Whole units use stable Y/X/Z cell order,
with a rotating remainder across metal layers, keeping each cell within its 108-unit
capacity. Only units assigned to retained cells survive. No removed-cell units are moved
into survivors. Remaining pooled liquid may then equalize normally in its smaller layout.
The anchor is persisted and does not move merely because the vessel expands.

Existing active Controller NBT remains supported. It gains only an optional anchor key;
old saves choose a deterministic anchor. Unchanged tanks/casting/fuel assets are preserved.
Changes affect future edits, not already-lost metal from earlier Controller destruction.

## Verification

The opt-in `verification/equipment.init.gradle` suite loads effective recipes and native
loot, exercises actual production removal callbacks in an isolated map world, and checks
split/invalid shapes, rapid removals, recursive drop counts, nine fill thresholds, 648
unit-conservation cases, SavedData reload/claim, existing client update tags, and 160 mining
increments. Existing fuel, ore, equipment, casting and loot regressions also run.

Minecraft tests remain: real player timing with effects/tools and interruptions; Creative;
explosions and chunk boundaries; save/restart; simultaneous multiplayer edits and visual
updates on reconnection. The isolated world tests model world storage/drop insertion;
they do not constitute live multiplayer, explosion-engine or visual verification.
